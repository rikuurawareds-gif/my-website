# システム構成

## 2種類の「Claude」を使い分ける
| | 役割 | 動き方 |
|---|---|---|
| **Claude Code**（`.claude/agents/` の担当たち） | 社内チーム。サービスを作る・直す・設計する・社内の判断材料を作る | オーナーやPMが呼んだとき、またはスケジュール実行で動く |
| **Claude API**（サーバーから呼ぶ） | 商品そのもの。表記チェック、レポートのコメント、Chatwork の返信下書き | 24時間、イベント（メッセージ受信・定期実行）に反応して動く |

顧客に提供するものは、常に動くサーバーと Claude API で作る。Claude Code はそれを作り運用するチームになる。

## 構成図
```
[Chatwork] ──Webhook──▶ 受信API ──▶ ジョブキュー ──▶ ワーカー ──▶ Claude API
[転送メール] ──────────▶   │                          │
[Drive の CSV] ◀──定期──── スケジューラ ─────────────▶│
                                                       ├──▶ DB（顧客・メディア・案件・メッセージ・指摘）
                                                       ├──▶ Drive（顧客フォルダにレポート）
                                                       └──▶ 承認キュー ──▶ 社内承認ルーム（Chatwork）
クローラー（表記チェック）── 公開記事 ──▶ ワーカー
```

## 技術の選択（初期）
| 部品 | 選択 | 理由 |
|---|---|---|
| 受信API・ワーカー | Google Cloud Run（またはCloudflare Workers） | 使った分だけの課金。Drive・Sheets との相性が良い |
| スケジューラ | Cloud Scheduler | 表記チェックの定期実行、月次レポート |
| DB | Firestore（顧客数が増えたら Postgres に移行） | 小さく始められる |
| ファイル | Google Drive（顧客と共有するもの） | 顧客がそのまま開ける |
| 秘密情報 | Secret Manager | Chatwork トークン、Claude API キー |
| 社内UI | 最初は Chatwork の承認ルーム + スプレッドシート | 管理画面を作る前に回るか確かめる |

## 承認キューの動き
1. ワーカーが返信の下書きを作り、顧客の自律レベル（L0〜L3）と内容の分類から「自動送信」か「承認待ち」かを決める。
2. 承認待ちは社内承認ルームに「顧客名・相手・元のメッセージ・下書き・理由」を投稿する。
3. 承認者が「OK」「修正: …」「却下」と返すと、それに従って送信・修正・破棄する。
4. 送ったもの・直したものはすべて記録し、プロンプト改善に使う。

## セキュリティ
- 顧客ごとにデータを分ける（すべてのレコードに顧客IDを付け、他社のデータを参照しない）。
- 顧客のASP管理画面のログイン情報は預からない。
- Chatwork のメッセージ本文は、目的（運用代行）以外に使わない。保存期間を契約で決める。
