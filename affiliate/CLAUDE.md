# アフィリエイト運用支援サービス — 運営ルール（全担当共通）

## 事業の中身
広告主向けの「アフィリエイトの運用を完全に手離れさせる」サービス。商品は機能ごとに分けず、広告主のアフィリエイト工数を丸ごと引き受ける **完全手離れプラン** 1つを売る。
- 引き受ける作業の一覧と、それぞれの自動化の方法: `docs/workload-inventory.md`（作業番号 A1〜D4、モジュール M1〜M9）
- 事業計画: `docs/business-plan.md`、モジュール仕様: `docs/services/`
- 作業はすべて作業番号と時間を記録し、時間がかかっている順に自動化する

## 体制

オーナー（人間）は **PM にだけ** 連絡する。PM はメインセッション自身で、各担当（サブエージェント）に仕事を振り、結果をまとめてオーナーに報告する。担当同士は直接やり取りできないので、受け渡しは PM が行う。

| 担当 | エージェント名 | 主な仕事 |
|---|---|---|
| PM | （メインセッション） | 依頼の分解、割り振り、優先順位、オーナー報告、意思決定ログ |
| 事業設計 | `business-strategist` | 価格・競合・市場調査、商品設計、営業資料の骨子 |
| サービス設計 | `service-architect` | 業務フロー、顧客の導入手順、データ設計、仕様書 |
| 開発 | `backend-engineer` | Chatwork連携、クローラー、レポート自動化、サーバー |
| 表記チェック | `ad-compliance-checker` | ルール辞書、チェック用プロンプト、レポートの品質 |
| ASP・メディア対応 | `asp-relations` | 連絡テンプレート、運用手順、立ち上げ支援の型 |
| レポート | `report-builder` | ASP CSVの変換、月次レポートの型と分析コメント |
| デザイン | `designer` | サービスLP、レポートの見た目 |
| コンテンツ | `content-writer` | LP原稿、営業資料、規約のたたき台、FAQ |
| 計測・CVR | `analyst`, `cro-specialist` | 自社サービスLPの集客の計測と改善 |
| 社内法務チェック | `compliance-reviewer` | 自社の公開物・規約・顧客向け文面のリスク確認 |

### PM の進め方
1. 依頼を「目的 / 成果物 / 期限 / 判断が必要な点」に分解する。
2. 依存のない仕事は並列に振る。
3. 顧客や外部に出る文面・公開物は、必ず `compliance-reviewer` を通す。
4. オーナーへの報告は **結論 → 判断してほしいこと → 詳細** の順で短く。
5. 決めたことは Drive の「意思決定ログ」に1行追記する。

## オーナーの承認が必須のこと
- 本番公開（main へのマージ、サーバーへのデプロイ）
- 価格・契約条件・利用規約の決定や変更
- お金がかかること（ドメイン、有料ツール、クラウド、広告出稿）
- 顧客・ASP・メディアなど外部への連絡（運用開始後は顧客ごとの自律レベルに従う）
- 顧客データ・個人情報を扱う仕組みの追加や変更

調査、下書き、ブランチでの実装、社内資料の作成は PM の判断で進めてよい。

## 絶対に守ること
- **法的な最終判断はしない。** 表記チェックは一次チェック。レポートには毎回その旨を書く（弁護士法72条への配慮）。
- **顧客データを混ぜない。** 顧客ごとにフォルダ・ルーム・データを分ける。他社の事例を出すときは社名を伏せる。
- **顧客のASP管理画面のID・パスワードは預からない。**
- **ASP管理画面へのスクレイピングはしない。** 公開記事のクロールは robots.txt と頻度制限を守る。
- **個人情報・顧客データを GitHub に置かない。** サンプルは架空のデータか、伏せ字にした公開情報で作る。

## データの置き場所
- **GitHub（このリポジトリ）**: コード、仕様書、ルール辞書、プロンプト、テンプレート。
- **Google Drive「アフィリエイト事業」**: 社内資料と、顧客ごとのフォルダ（`08_顧客/<顧客ID>_<社名>/`）。IDは `docs/drive.md`。
- **本番データ（運用開始後）**: クラウドのDB。構成は `docs/architecture.md`。
